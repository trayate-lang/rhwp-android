# 옆에서 함께 배우는 개발 기록

## 1. 환경과 원본 고정

코드는 재료이고 빌드 도구는 조리 도구다. 같은 재료여도 도구 버전이 다르면 결과가 달라질 수 있다.
그래서 원본 커밋, Rust/WASM, Node, Java와 Gradle 버전을 기록한다.
이 원리는 서버 배포, 데이터 분석, 자동화에서도 같다. 문제를 재현하려면 입력과 실행 환경을 알아야 한다.

`clone`은 GitHub 코드를 Mac에 가져온다. `sparse-checkout`은 큰 저장소에서 지금 필요한 폴더만 펼친다.
`origin`은 내가 수정할 Fork, `upstream`은 업데이트를 참고할 원본을 가리키는 별명이다.

계정 확인 성공과 저장소 생성 성공은 다르다. GitHub의 `403`은 로그인 여부 외에 권한도 확인해야 한다는 신호다.
비밀번호/토큰을 코드나 로그에 넣어서 해결하지 않는다.

## 교육 약속

의미 있는 단계마다 현재 작업, 필요한 개념, 선택 이유와 불확실성, 다른 분야에의 적용, 검증 근거를 설명한다.
오류는 관찰 → 가설 → 구별할 검사 → 결과 순서로 설명하고 추측과 확인을 구분한다.

## 2. 웹 편집기를 앱에 연결하기

공통 원리: 화면, 문서 내용, 저장 장치는 서로 다른 책임이다. 기존 편집기는 문서 편집을, Android는 파일 선택과 OS 공유·인쇄를 맡는다. 연결부의 작은 계약만 맞추면 같은 엔진을 여러 환경에서 재사용할 수 있다.

이번 선택: WebViewAssetLoader로 APK의 웹 화면을 HTTPS 형태의 로컬 주소에 제공한다. 엔진과 글꼴도 함께 넣고 INTERNET 권한을 선언하지 않는다. 웹과 Android 사이에는 256KiB씩 바이트를 나눠 보내 큰 문자열 메시지를 피한다.

저장에서는 begin(준비) → append(조각 전달) → finish(실제 저장·재읽기 확인)의 단계가 있다. 쇼핑 주문이나 파일 업로드에서도 요청 접수와 최종 완료를 구분한다. 파일 선택 취소는 AbortError로 돌려줘 오류나 성공으로 잘못 처리하지 않는다.

## 3. 폴더블과 상태의 수명

화면 크기가 바뀌어도 문서 엔진을 다시 만들 필요는 없다. 이 앱은 크기·방향 변화 때 같은 WebView를 유지하므로 메모리에 있는 커서·undo·수정 상태가 살아 있다. 프로세스가 종료되는 상황은 별도이며, 그때는 완료된 IndexedDB 복구 사본을 사용한다.

일반적으로 반응형 UI는 공간 배치 문제이고 상태 복원은 데이터 수명 문제다. 웹의 창 크기 변경, 태블릿 분할 화면, 서버 재시작에서도 두 문제를 구분해 설계한다.

## 4. 테스트에서 배운 점

Node 26에서 실패한 원본 테스트를 바로 수정하지 않았다. 실패 메시지가 제거된 Node 옵션과 누락된 fixture를 가리켰기 때문이다. Node 24와 원본 테스트 입력으로 바꾸자 1,367개가 통과했다. 오류를 고치기 전에 코드 문제와 환경 문제를 나눈 사례다.

에뮬레이터 첫 화면에서는 하단 버튼이 상태 표시줄을 덮었다. 타입 검사로는 화면 배치를 알 수 없어 실제 렌더링과 좌표를 확인하고 높이를 조정했다. 접기·펼치기 10회 뒤에는 텍스트만 비교하지 않고 커서·확대·dirty·undo와 실제 undo/redo 결과를 비교했다.

## 5. GitHub를 언제 쓰는가

Fork는 원본과 연결된 내 저장소다. Clone은 코드를 Mac에 가져온다. Branch는 같은 원본에서 변경을 나누는 이름이고, Commit은 변경 내용과 이유를 기록하는 체크포인트다. Push는 로컬 기록을 GitHub로 보내는 작업이다. Commit만 하고 Push하지 않으면 GitHub에는 아직 보이지 않는다.

이번 환경에서는 브라우저/터미널/연결 도구의 인증 권한이 서로 달랐다. trayate-lang 로그인 확인만으로 터미널 토큰의 쓰기 권한을 가정할 수 없었다. 기존 토큰을 넓히지 않고 GitHub 연결 도구의 Git 객체 API로 게시하고, 로컬 Git은 같은 원격 기록으로 동기화한다. 일반적인 개발 환경이라면 저장소에 대한 쓰기 권한을 갖춘 인증으로 `git push origin android/offline-editor`를 사용한다.

Issue #1은 요구와 남은 검사를 기록한다. PR은 구현 브랜치와 android-main의 차이를 검토하는 화면이다. Actions는 내 Mac과 별개 환경에서 동일 빌드를 재현한다. Artifact는 해당 실행의 검사 보고서를 받는 곳이다. Merge는 검토한 변경을 통합 브랜치에 받아들이는 작업이다.

원본 업데이트는 바로 덮어쓰지 않고 upstream 갱신 → 별도 브랜치 → Android 검증 → PR 순서로 진행한다. 특히 원본의 배포 workflow가 되살아나지 않도록 확인한다.
